# Next.js Engine v2.6.2 — Cross-Browser, Hydration & Runtime Stability

> **Status:** Prepared bug-fix release  
> **Release type:** Compatibility + correctness patch  
> **Previous patch:** v2.6.1  
> **Recommended tag:** `Release-v2.6.2`

v2.6.2 is the stability pass for the v2.6 generation of Next.js Engine.

The release started with an EngineScroll Timeline bug found in the documentation progress UI, then expanded into a wider compatibility audit across EngineScroll, EngineTransitions+, EngineCanvas, React 19 hydration, Next.js App Router navigation, EngineOverlay, mobile viewport behavior, browser fallbacks, and release-time CI.

The goal is not to remove advanced Engine behavior to make compatibility easier. The goal is to keep the same NE architecture while making each feature behave correctly under real React, browser, display, and device conditions.

---

## Release highlights

- EngineScroll Range/Timeline `#id` targets now behave like navigation and fall back to ordinary DOM ids.
- `viewport.current` now defaults to progressive document-aware focus instead of permanent screen center.
- EngineScroll late mounts, dynamic DOM movement, resize invalidation, URL protocol handling, snapping, subscriber isolation, and physical velocity semantics are hardened.
- Transitions+ no longer depends on CSS typed multiplication for complex presets.
- Transitions+ now has collision-safe shared element names.
- Browsers without native View Transitions receive a Web Animations fallback instead of losing all transition feedback.
- Broken custom transition animation falls back to safe fade/skip behavior without blocking navigation.
- Same-URL animated navigation no longer waits for a URL mutation that cannot happen.
- `useEngineTransitions().run()` is lifecycle-safe when driven from React effects, EngineScroll-derived state, observers, timers, subscriptions, or external stores.
- EngineCanvas now detects high-refresh RAF cadence instead of judging every display with 60 Hz assumptions.
- EngineCanvas callback timing now exposes stable `elapsed`, measured FPS, average FPS, and detected refresh rate.
- EngineCanvas no longer injects a fake 16 ms first/resume frame and no longer forces the 2D `desynchronized` hint by default.
- Generated Engine CSS is serialized deterministically and hydration adopts the exact server stylesheet before client reconciliation.
- Initially-open Dialog/Drawer/Popover portals no longer create different server and first-client trees.
- Overlay `lockScroll` can change while the overlay stays open.
- Popovers understand `visualViewport` for mobile keyboards, browser chrome, and zoomed visual viewports.
- Legacy EngineScroll reduced-motion behavior is hydration-safe.
- EngineNav active state is rewrite-safe during hydration and route matching is segment-aware.
- EngineScroll no longer globally takes ownership of browser/Next.js history scroll restoration.
- React 19 theme/font stylesheet resources use explicit precedence and deduplication identities.
- Real browser CI covers Chromium, Firefox, and WebKit with Playwright.
- Package metadata moves to `2.6.2` and requires the current secured Next.js 16.3.3 patch line.

# EngineScroll fixes

## 1. Range/Timeline normal DOM ids

Before v2.6.2:

```ts
EngineScroll.move("#hero");
// normal DOM id worked

EngineScroll.timeline({
	start: "#hero",
	end: "#features",
});
// could remain invalid unless both ids were registered EngineScroll points
```

Range and Timeline now use the same target semantics as navigation:

```text
number / top / bottom / current
	↓
registered EngineScroll point
	↓ when missing
normal DOM element id
	↓
alignment + offset
```

Registered points still take precedence when a registered point and DOM id share a name.

## 2. Late-mounted targets

An unregistered DOM target that does not exist on the first Timeline/Range read is no longer permanently remembered as missing.

Lazy and Suspense content can mount later and become valid without recreating the Timeline.

## 3. Moving DOM boundaries

Plain DOM ids are not owned by `EngineScrollPointManager`, so they do not have its explicit geometry invalidation lifecycle.

v2.6.2 therefore treats ordinary DOM boundaries as live geometry while retaining the cached path for registered EngineScroll points.

## 4. Progressive viewport focus

The historical default was:

```ts
focus = 0.5;
```

which permanently defined `viewport.current` as screen center.

The v2.6.2 default is:

```ts
"progressive"
```

calculated from physical document scroll progress:

```ts
maximumScroll = Math.max(0, documentHeight - viewportHeight);
focus = maximumScroll === 0
	? 0
	: clamp(scrollY / maximumScroll, 0, 1);
```

That produces:

```text
document start   → focus 0.00
document 25%     → focus 0.25
document halfway → focus 0.50
document 75%     → focus 0.75
document end     → focus 1.00
```

Public control:

```ts
EngineScroll.setFocus("progressive");
EngineScroll.setFocus("top");
EngineScroll.setFocus("center");
EngineScroll.setFocus("bottom");
EngineScroll.setFocus(0.35);

EngineScroll.getFocus();
EngineScroll.getFocusMode();
```

Applications that intentionally depend on the historical permanent-center definition can opt back in with `EngineScroll.setFocus("center")`.

## 5. Physical velocity remains physical

Once `viewport.current` became dynamic, using it for scroll velocity would mix logical focus motion into physical scroll motion.

Velocity and direction now measure the physical viewport top edge instead.

## 6. Resize invalidation

Resize/orientation handling previously risked writing the new dimensions before the central measurement pass compared old and new geometry.

The central browser measurement pass now remains the owner of cache writes and point invalidation.

## 7. SSR hash safety

`EngineScrollHash.moveToHash()` now fails safely outside the browser rather than touching browser globals from SSR paths.

## 8. URL protocol prefix

The Engine protocol only recognizes:

```text
#-es?
```

instead of broadly capturing every hash beginning with `#-es`.

Normal anchors such as `#-essay` or `#-eslint` are no longer mistaken for EngineScroll commands.

## 9. URL intent preservation

A protocol hash is cleaned only after movement succeeds.

If the requested target has not mounted yet, the URL is not silently erased.

## 10. Snap ownership

Each automatic snap session now owns a unique lifecycle token. Disposing an older snap session cannot disable a newer session that replaced it.

## 11. Standalone directional snap

One-shot directional snapping now uses the current runtime scroll direction when no auto-snap direction history exists.

## 12. Subscriber isolation

One throwing EngineScroll subscriber no longer prevents later subscribers from receiving the same runtime frame.

## 13. Browser lifecycle without global history takeover

EngineScroll initialization is connected, but v2.6.2 deliberately **does not** globally set:

```ts
history.scrollRestoration = "manual";
```

Next.js and the browser retain history restoration ownership unless an Engine feature explicitly performs a scroll movement.

This avoids NE silently taking responsibility for Back/Forward restoration without implementing a complete session-history restoration system.

# EngineTransitions+ compatibility fixes

## 14. Removed typed CSS multiplication dependency

Complex preset frames previously generated values such as:

```css
calc(-1 * 10deg)
calc(-.35 * 36px)
calc(.5 * 7px)
```

That unnecessarily depended on newer CSS typed arithmetic support even when the browser already supported View Transitions.

v2.6.2 performs those calculations in JavaScript and emits ordinary values such as:

```css
-10deg
-12.6px
3.5px
```

The change applies to complex `liquid`, `depth`, `flip`, `page-turn`, `scatter`, `rgb`, and `portal` frames.

## 15. Collision-safe shared transition names

Shared DOM ids are sanitized before becoming `view-transition-name`s. Sanitization alone could collapse different ids to one name:

```text
Foo Bar
foo-bar
```

Long ids could also collide after truncation.

v2.6.2 appends a deterministic hash of the original id, preserving readable names without allowing those collisions.

## 16. Safer custom-animation fallback

If a browser exposes View Transitions but rejects the requested NE pseudo-element animation, the fallback order is now:

```text
requested preset
	↓ failure
safe fade
	↓ failure
skip custom animation
	↓
complete update/navigation
```

The previous behavior could retry nearly the same failing mechanism and leave the transition with no useful visual fallback.

## 17. Browsers without native View Transitions

Transitions+ now has a compatibility tier between full native transitions and completely instant navigation.

```text
native View Transitions
	→ full NE captured-page preset

no native View Transitions + Web Animations
	→ short root fade around the real update/navigation

no compatible animation API
	→ normal update/navigation
```

This allows older Firefox/Safari/Chromium-family builds that lack `document.startViewTransition` to keep a small amount of transition feedback without a third-party polyfill.

## 18. Same-URL transition stall

Animated `push()` / `replace()` now normalize the requested URL before waiting for navigation.

If the destination is already the exact current URL, NE lets the router handle it immediately instead of waiting 650–2200+ ms for an impossible URL change.

## 19. Update callback failures are preserved

Errors from a View Transition update callback are no longer silently swallowed by the transition-finished path. The navigation/update lifecycle still cleans itself up, then the update failure is allowed to propagate.

### Lifecycle-safe `run()` calls

The Kastrick product demo exposed a separate React lifecycle edge case: `useEngineTransitions().run()` wrapped its state update in `flushSync()` immediately, so calling `run()` from a passive effect could make React report:

```text
flushSync was called from inside a lifecycle method
```

`run()` now yields one Promise microtask before entering the transition. That moves the synchronous snapshot update out of React's current render/commit stack while still running before the next paint in normal event-driven usage.

This makes effect-driven patterns valid without application workarounds:

```tsx
useEffect(() => {
	void transitions.run(
		() => setActiveIndex(sceneIndex),
		"slide",
	);
}, [sceneIndex, transitions]);
```

The same path covers EngineScroll-derived state, observers, timers, async/subscription reactions, and external stores.

# EngineCanvas high-refresh fixes

The interactive Kastrick EngineCanvas demo exposed a separate timing problem on high-refresh displays. The canvas runtime already used `requestAnimationFrame`, so the loop itself was not intentionally capped at 60 FPS. The actual problems were **60-Hz assumptions around that RAF loop** plus a demo clock formula that amplified variable frame intervals.

## Refresh-aware RAF measurement

EngineCanvas now measures the real recent RAF cadence and estimates common display refresh rates such as 60, 90, 120, 144, 165, 180, 200 and 240 Hz.

Occasional dropped frames do not immediately collapse a 120 Hz estimate to 60 Hz. The estimator prefers the faster end of recent valid intervals so a stream containing mostly ~8.3 ms frames with some ~16.7 ms frames still identifies as a 120 Hz-capable cadence.

## Adaptive DPR follows the display target

The old adaptive quality logic used fixed thresholds:

```text
below ~32 FPS → lower DPR
above ~56 FPS → recover DPR
```

That is reasonable on a 60 Hz display, but on a 120 Hz display a surface stuck near 60 FPS looked "healthy" to the adaptive system.

The default is now:

```tsx
<EngineCanvas adaptive adaptiveTargetFps="display" />
```

and thresholds scale relative to the detected cadence. Applications can still choose an explicit target such as `adaptiveTargetFps={60}` when they intentionally want a lower rendering budget.

## Stable frame clock

`onDraw` receives a backward-compatible fifth argument:

```ts
onDraw={(context, canvas, delta, frame, timing) => {
	const seconds = timing.elapsed * .001;
}}
```

The timing object exposes:

```ts
interface EngineCanvasFrameInfo {
	timestamp: number;
	delta: number;
	elapsed: number;
	fps: number;
	averageFps: number;
	refreshRate: number;
}
```

The first frame after startup/resume now uses `delta = 0` instead of a synthetic 16 ms value, and hidden/offscreen pause time is not injected into active animation elapsed time.

## 2D presentation synchronization

Normal 2D EngineCanvas previously always requested `desynchronized: true`. That browser hint can trade compositor synchronization for lower latency and can appear as tearing/previous-frame presentation on some mobile/high-refresh combinations.

The default is now synchronized:

```tsx
<EngineCanvas desynchronized={false} />
```

Low-latency users can still opt into `desynchronized` explicitly.

## `frame * delta` timing bug

A variable frame delta must not be multiplied by the total frame count to create absolute time:

```ts
// incorrect on variable/high-refresh cadence
const time = frame * delta;
```

When a 120 Hz stream alternates between ~8.3 ms and an occasional ~16.7 ms frame, that formula can make the derived absolute time jump backward/forward because the current frame's interval is applied to every historical frame.

The Kastrick demo was updated to use EngineCanvas's stable elapsed clock instead:

```ts
const time = timing.elapsed * .001;
```

# React 19 / Next.js hydration stability

## 20. Deterministic generated CSS serialization

`StyleCollector` no longer serializes CSS purely in the accidental order components happened to register rules during one render traversal.

Equivalent sets of generated rules now produce a canonical ordering.

This matters under React 19 because rendering can be suspended, restarted, or traversed differently between server rendering and client hydration.

## 21. Server stylesheet adoption during hydration

`EngineCollectedStyles` now uses the exact server-emitted stylesheet text as its initial browser hydration value when that stylesheet already exists in the document.

After mount it reconciles to the deterministic collector snapshot and subscribes for newly generated client rules.

The fix deliberately does **not** use `suppressHydrationWarning`.

## 22. Dynamic generated rules can flush after mount

A provider-scoped collector now has a deferred subscriber path. CSS registered by later client state/lazy content can update the Engine stylesheet without setting React state during another component's render.

## 23. Initially-open Overlay hydration

Dialog, Drawer, and Popover no longer read `document.body` to choose a portal target during render.

Portal ownership is resolved after mount:

```text
SSR                 → no portal target
first client render → no portal target
mounted client      → resolve portal target and render portal
```

This keeps `defaultOpen: true` from creating different server and first-client trees.

## 24. Legacy EngineScroll reduced motion

The older schema `EngineScroll` component now begins with a hydration-stable reduced-motion value and applies the real browser media preference after mount.

A server render no longer assumes one transition style while the very first client render assumes another.

## 25. EngineNav rewrite-safe active state

Next.js rewrites can make the pathname visible during prerendering differ from the pathname visible in the browser.

EngineNav now keeps pathname-dependent active styling neutral during SSR/first hydration and applies the live `usePathname()` result after mount.

## 26. Segment-aware EngineNav route matching

Active matching now understands route boundaries:

```text
/about       matches /about
/about       matches /about/team
/about       does NOT match /about-us
/product     does NOT match /productivity
```

Root `/` remains exact-only.

# Overlay and mobile compatibility

## 27. Live `lockScroll`

Body scroll locking has its own effect lifecycle.

Changing `lockScroll` while a Dialog/Drawer remains open now actually locks or unlocks the page without needing to close the overlay first.

## 28. Mobile visual viewport positioning

Popover positioning now uses `window.visualViewport` when available, including:

- visible viewport width/height;
- viewport offsets;
- visual viewport resize events;
- visual viewport scroll events.

This improves behavior when a software keyboard opens, mobile browser chrome changes size, or the user zooms the page.

Browsers without `visualViewport` retain the existing `window.innerWidth` / `window.innerHeight` path.

# React 19 stylesheet resources

## 29. Theme/font stylesheet precedence

Engine theme fonts now provide React 19 stylesheet `precedence` metadata.

Inline Engine theme CSS receives a deterministic content identity plus stylesheet precedence so nested/reused themes can be deduplicated by React rather than producing duplicate fixed `__engine_theme__` ids.

# Browser compatibility policy

v2.6.2 separates **application compatibility** from **maximum visual transition capability**.

An NE application does not require native View Transitions to navigate.

```text
Chromium / Brave / Edge / Opera family
	→ native effect when engine version supports it
	→ WAAPI/simple fallback otherwise

Firefox
	→ native effect on modern View-Transition-capable builds
	→ WAAPI/simple fallback on older builds

Safari / WebKit
	→ native effect on modern View-Transition-capable builds
	→ WAAPI/simple fallback on older builds
```

NE does not claim support for browsers outside the underlying React 19 / Next.js 16 browser support floor. The fallback exists to make the transition feature less restrictive than the rest of the application, not to make Next.js 16 run on legacy engines it does not support.

Full policy: [`../engine-components/enginetransitions-compatibility.md`](../engine-components/enginetransitions-compatibility.md).

# Real-browser CI

A Playwright matrix runs the compatibility harness in:

```text
Chromium
Firefox
WebKit
```

The browser suite checks:

- real SSR → client hydration;
- generated Engine CSS;
- initially-open Dialog portals;
- lifecycle/effect-driven `Transitions+.run()` state updates;
- absence of React's lifecycle `flushSync()` warning;
- a complex `liquid` transition;
- animated route navigation;
- same-URL navigation completion;
- native-View-Transition-disabled fallback;
- reduced-motion navigation;
- browser page errors;
- hydration-related console errors.

The Playwright server readiness probe checks the ordinary root route; the compatibility page is exercised by the tests themselves so route compilation cannot block server detection.

Node smoke coverage also rejects typed CSS multiplication, guards the lifecycle-yield-before-`flushSync()` contract, tests deterministic StyleCollector output, and now exercises EngineCanvas 60/120/144 Hz cadence detection plus dropped-frame and pause/resume behavior.

# Compatibility / migration notes

The only intentional EngineScroll behavior change is the default definition of `viewport.current`.

To keep the old permanent center behavior:

```ts
EngineScroll.setFocus("center");
```

Transitions+ does not require application changes. Browsers with native View Transitions continue using the full preset path; less capable browsers degrade automatically. Effect/subscription-driven `run()` calls no longer need timer or animation-frame workarounds.

EngineCanvas continues using `requestAnimationFrame`; no application-side 120 Hz timer is required. Existing four-argument `onDraw` callbacks remain valid. Consumers that derive absolute animation time should use the new fifth-argument `timing.elapsed` or accumulate `delta` instead of using `frame * delta`. `desynchronized` is now opt-in for Canvas 2D.

EngineNav route matching becomes more precise. If an application intentionally relied on prefix matching such as `/about` being active on `/about-us`, set the item's `active` field explicitly instead.

No migration is required for Dialog, Drawer, Popover, Range, Timeline, registered points, or ordinary Engine links.
